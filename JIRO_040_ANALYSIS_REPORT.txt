JIRO v0.4.0 — VERSION ANALYSIS AND 0.3.3 COMPARISON
================================================================================
Analyzed: 2026-10-22
Method:    source inspection, test execution, live CLI invocation
Baseline:  jirosearch 0.3.3 (committed, main @ e60207a)
Candidate: 0.4.0 work-in-progress (uncommitted, branch fix/stress-test-findings)

--------------------------------------------------------------------------------
HEADLINE
--------------------------------------------------------------------------------

A large, genuinely engineered body of work exists — 21,504 lines of new code
across 8 new modules, 488 passing tests, 13 ADRs, 16 client adapters. The
architecture is real and the engineering is disciplined.

It is NOT ready to ship as 0.4.0, and nothing is committed:

  1. All four headline performance claims have NO benchmark artifact.
     The project's own CLAIMS.md rule says such numbers may not be published.
  2. The flagship feature (graph run) fails on a trivial query.
  3. The version is still 0.3.3 in every file. Nothing is bumped.
  4. The entire body of work is uncommitted — 0 commits on the branch.

Verdict: strong Phase 1-4 engineering, presented with pre-launch ambition that
the evidence does not yet support. The gap is verification and tuning, not
architecture.

--------------------------------------------------------------------------------
4.2 CRITICAL — Flagship feature fails on a trivial query
--------------------------------------------------------------------------------
Command: jiro graph run "what is the capital of France"
Result:  HTTP 502, graph_execution_failed, rc=1

Both search nodes timed out. Root cause is a budget/latency mismatch:

  Graph total deadline (model.py:41)      : 2,500 ms
  Effective per-node deadline (observed)  : 1,400 ms
  Real search latency (measured live)     : 4,630 - 12,905 ms

The node budget is roughly 3x to 9x BELOW the actual search latency floor.
On this machine and network, the graph cannot succeed for any web search.

To the project's credit, the failure is honest — it reports 502, node_timeout,
explicit gaps, empty results, and packet:null. Nothing is faked. The principles
in MASTER_PLAN section "Fail visible" are upheld. But the default budget needs
calibration against real latency before this feature is usable.

4.6 LOW — Live config warning on new runtime code
--------------------------------------------------------------------------------
Every `jiro tasks` invocation prints:
  "runtime.lease_ttl_seconds is not greater than
   runtime.max_attempt_timeout_seconds; a long attempt that blocks the event
   loop could be reclaimed and re-executed"

The runtime's own validator (jiro/runtime/config.py:228) detects a genuine
safety hazard in its default configuration and warns. Defaults are
mis-configured relative to each other. Relevant because it directly describes
a duplicate-execution risk.

6. ARCHITECTURE ASSESSMENT
================================================================================

The 6-layer design in MASTER_PLAN is coherent:

  L6 Agent Fabric    — 16 adapters, sessions, one-command setup     [built]
  L5 Parameter Layer — params, TTL, decay, diff                     [built]
  L4 Evidence        — claims, support, packets, ledger             [built]
  L3 Graph Runtime   — planner, cost model, waves, deadline         [built, mistuned]
  L2 Sense           — engines, plugins, social, proxies, SSRF      [unchanged]
  L1 ...             — storage                                      [unchanged]

Strengths worth naming:
  - "Additive only" is respected: no existing engine, endpoint or SDK shape
    was broken by any of the 8 new modules.
  - The capability ladder (R0-R4) is a far more honest framing than an "AGI"
    claim, and the plan explicitly refuses the AGI label.
  - ADR 0011 draws a clear line around what "internet as model parameter"
    does NOT mean, preventing the most likely overclaim.
  - Failure reporting is genuinely honest: node_timeout, gaps, engine
    attribution, budget accounting — all surfaced.

Weakness:
  - The plan's ambition (2x/3x, 15+ agents, R3) is written as though shipped,
    while the evidence tier is empty. The writing runs ahead of the artifacts.

7. RECOMMENDED SEQUENCE BEFORE 0.4.0 CAN SHIP
================================================================================

Priority 1 — Protect the work (minutes)
  1. Commit the current tree to the branch. 21,504 lines with no commit is the
     single largest risk in this analysis.

Priority 2 — Make the flagship work (days)
  2. Calibrate the graph node budget against measured latency. Current default
     (1400ms/node) cannot serve web search (4,600-12,900ms). Either raise the
     budget, make it adaptive, or have the planner estimate from observed
     engine latency before committing to a plan.
  3. Re-run: jiro graph run "what is the capital of France" must return a cited
     packet, not a 502.

Priority 3 — Earn the claims (days)
  4. Run benchmarks/run.py to generate the four artifacts, or delete the
     claims from the public docs until they can be produced. Publishing
     "2x faster" with no artifact contradicts the project's own CLAIMS.md.
  5. Resolve the runtime lease_ttl / max_attempt_timeout default mismatch —
     it warns about duplicate-execution, which matters for a durable runtime.

Priority 4 — Ship hygiene (hours)
  6. Bump version to 0.4.0 across pyproject.toml, jiro/__init__.py,
     npm/package.json, sdk/python/setup.py once features are frozen.
  7. Implement or remove the "handoff protocol" claim from MASTER_PLAN.

================================================================================
8. BOTTOM LINE
================================================================================

0.4.0 is a real, substantial, well-architected expansion — not a plan document
dressed up as code. 21,504 lines, 488 passing tests, 16 working client
adapters, and 13 ADRs show disciplined engineering. The planner demonstrably
works and reasons about tradeoffs.

The gap between 0.3.3 and 0.4.0 is genuine in capability: from a search-and-
scrape API to a query-graph runtime with evidence compilation, durable tasks,
agent orchestration, and a memory subsystem.

But 0.4.0 is not shippable today for three reasons, in order of severity:

  1. Zero of four headline claims have their required artifact. The project
     wrote a rule forbidding this and then did it.
  2. The flagship graph feature fails on "what is the capital of France"
     because its budget is 3-9x below real search latency.
  3. Nothing is committed and nothing is versioned.

None of these are architectural problems. All three are finish-line problems —
protect the work, tune the budget, run the benchmark. The foundation is sound;
the last mile is not walked.
